# DumpTrace 反查技术路径

> 目标：从展锐/UIS 类 `*_armlog` 死机包，定位到「线程 → Fault → PC/LR 符号 → 死机前业务时间线 → 根因假设」。
> 本文先固化分析路径，后续再落成工具流水线。

---

## 1. 输入约定

典型现场包（示例）：

```text
dump_YYYY_MM_DD_HH_MM/
  xxx.axf                          # 与死机版本匹配的符号
  YYYY_MM_DD_HH_MM_SS_mmm_armlog/  # Logel 导出目录
    *.ass                          # 断言/异常现场（优先）
    *.logel                        # 业务/协议日志容器
    *_1.mem                        # 内存镜像
    *_log_stat.txt                 # 抓 log 丢包统计
    *.lst                          # 工具/解析库版本
    YYYY_.../                      # Logel 解析缓存（traceview/msgview）
    YYYY_..._pb/                   # playback 副本（通常等价）
```

硬性前置：

1. `.axf` 与死机固件版本一致（工程名/编译时间可对 ASS 内 Version）。
2. 优先分析非 `_pb` 主包；`_pb` 仅作备份或二次打开失败时的替代。
3. 丢包率高时（`*_log_stat.txt`），时间线可能有缺口，结论需留余地。

---

## 2. 总流程（建议工具化的 Stage）

```text
[Stage 0] 包校验
    ↓
[Stage 1] 解析 .ass → 异常画像（类型/线程/Fault/PC/LR）
    ↓
[Stage 2] .axf 符号反查 → 函数/文件/行号候选
    ↓
[Stage 3] .logel 时间线对齐 → 死机前 1~N 秒业务事件
    ↓
[Stage 4] （可选）.mem 深挖 → 栈回溯/对象/堆块
    ↓
[Stage 5] 汇总报告 → 根因假设 + 复现/验证建议
```

工具产品形态建议：CLI `dumptrace analyze <armlog_dir> --axf <path>`，输出结构化 JSON + 人类可读 Markdown。

---

## 3. Stage 0：包校验

检查项：

| 检查 | 说明 |
|------|------|
| 目录可识别 | 存在 `*.ass`，且为 armlog 布局 |
| 符号匹配 | `.axf` 文件名片段、ASS↔AXF 编译时间、Build ID（Project Version）、同 stem `.map` 入口点/摘要指纹；分项提示 |
| 体积合理性 | `.mem` 非 0；`.logel` 非空；空 `.iq`/无线 cap 可忽略 |
| 丢包 | 读 `*_log_stat.txt` 的 `Total lost` / `PS MTA lost` |

失败策略：缺 ASS → 中止；缺 AXF → 仅输出寄存器画像；缺 logel → 仅异常+符号。

---

## 4. Stage 1：解析 `.ass`（定性）

### 4.1 必提字段

从 ASS 文本/可打印串中抽取：

| 字段 | 示例（真实样本） | 含义 |
|------|------------------|------|
| Assert/Exception | `ASSERT(Abort exception handler !)` | 异常类别 |
| Exception PC | `Exception at 0x60127474` | 异常相关地址 |
| Fault 描述 | `Abort fault(DFSR:0x0000080f): Permission fault` | 故障类型 |
| Fault address | `0x00000004` | 非法访问地址 |
| Thread Name | `T_P_APP` | 出事线程 |
| Queue | `Q_P_APP` | 关联消息队列 |
| 寄存器 | `PC / R14(LR) / R0..R12 / CPSR` | 现场 |
| 版本 | `Project Version` / `Platform Version` / 编译时间 | 对齐符号 |
| 内存线索 | `rvosmem.c(384)` 等 | 堆/OS 相关提示 |

### 4.2 经验规则（可做成规则表）

| 模式 | 判读 |
|------|------|
| Fault address ∈ `{0x0, 0x4, 0x8, 0xc, …小偏移}` | 空指针成员访问（`NULL->field`）高概率 |
| DFSR Permission / Translation fault | MMU/非法地址/野指针 |
| Thread = `T_P_APP` | 优先查应用消息处理、关流/切模式竞态 |
| Assert 文案含 Abort exception handler | 硬件 Abort 进断言，而非业务 `SCI_ASSERT` 软断言 |
| 同包多次重复 assert 块 | 取第一份完整寄存器现场即可 |

### 4.3 Stage 1 输出（建议 JSON schema 雏形）

```json
{
  "crash_kind": "data_abort",
  "assert_msg": "Abort exception handler !",
  "fault": { "dfsr": "0x0000080f", "desc": "Permission fault", "addr": "0x00000004" },
  "thread": { "name": "T_P_APP", "queue": "Q_P_APP", "id": "0x15" },
  "regs": { "pc": "0x60022f48", "lr": "0x60127474", "r0": "0x0" },
  "version": {
    "project": "DEMO_V01_160_320_H_16MB_SW_COM_EX1234",
    "platform": "MOCOR_20B.CHIP_DEMO_W24.08.4_Debug"
  },
  "hints": ["null_deref_offset_4", "mem_hint:rvosmem.c"]
}
```

## 5. Stage 2：`.axf` 符号反查

### 5.1 目标地址集合

至少解析：

1. `PC`（当前指令）
2. `Exception at` / Abort 模式 `R14`
3. SVC 模式 `R14`（上一层业务返回）
4. （可选）栈上扫描得到的疑似代码地址（需先有 `.mem`）

### 5.2 反查手段（按环境可用性）

| 手段 | 命令/方式 | 输出 |
|------|-----------|------|
| fromelf | `fromelf -s xxx.axf` / 地址查表 | 符号名 |
| addr2line | `arm-none-eabi-addr2line -e xxx.axf -f -C -a <addr>` | 函数+文件:行 |
| readelf/nm | `nm -n xxx.axf` 后二分定位 | 最近符号 |
| IDE/Trace32 | 加载 axf + mem | 图形栈 |

注意：Thumb 地址可能需 `|1` 或清除 LSB 再查；MOCOR/RVDS 产物与 GNU 工具链兼容性要实测，工具内做多后端适配。

### 5.3 Stage 2 输出

```json
{
  "symbols": [
    { "addr": "0x60022f48", "func": "?", "file": "?", "line": null, "role": "pc" },
    { "addr": "0x60127474", "func": "?", "file": "?", "line": null, "role": "exception_lr" }
  ]
}
```

## 6. Stage 3：`.logel` 时间线对齐

### 6.1 打开方式

- 人工：Unisoc **Logel** 打开 `.logel` 或整个 `*_armlog` 目录。
- 工具化（后续）：解析 Logel 导出的 `traceview.dat` / `msgview.dat`，或调用官方解析库（若有授权）。

### 6.2 对齐策略

1. 以 ASS 时间 / 文件名时间戳为锚点（示例：`2025_10_10_14_19_49`）。
2. 取死机前窗口：默认 **3s / 10s / 60s** 三档可配。
3. 关键字过滤（可配置词表）：

```text
camera, preview, encode, stream, rtp, wifi, socket,
assert, abort, exception, null, free, mem,
T_P_APP, Q_P_APP, close, stop, start, switch
```

4. 输出「最后 N 条相关事件」+「最后一条成功路径事件」。

### 6.3 和业务场景的绑定（相机推流例）

优先回答：

- 死在开流、推流中、停流、切分辨率，还是断网？
- `T_P_APP` 在关会话后是否仍收到回调/消息？
- 是否有 buffer 归还/二次释放日志？

## 7. Stage 4：`.mem` 深挖（可选）

触发条件：

- 符号已指向某指针成员，需确认对象是否为 NULL/已释放；
- 怀疑栈溢出、堆破坏、use-after-free。

路径：

1. 读 ASS 中 `Stack_Start` / `Stack_End` / `Tcb_Addr`。
2. 从 `.mem` 映射：注意 dump 基址（样本中 `begin addr=0x80000000`）。
3. 回溯 SVC 栈；扫描可执行区间地址做二次符号反查。
4. 对照 ASS 内内存使用摘要（System/Static Total/Avail、段 ALLOC/FREE、`Allocated memory info` Top）看异常大块或泄漏趋势。 DumpTrace 已自动导出 `mem_usage.*`。

工具阶段可先做：地址翻译 + 十六进制窗口 + 栈上代码地址启发式提取。

## 9. 样本锚定（用于验收工具）

路径：`D:\path\to\dump_demo\`

已知金标准（人工已确认，工程标识为演示假数据）：

| 项 | 值 |
|----|----|
| 类型 | Data Abort → Assert |
| Fault addr | `0x00000004`（空指针+4） |
| 线程 | `T_P_APP` |
| PC | `0x60022f48` |
| Exception | `0x60127474` |
| 工程 | `DEMO_V01_..._EX1234` |
| 符号文件 | `CHIP_DEMO_V01_160_320_H_16MB_SW_COM_EX1234.axf` |

工具验收：对该包异常画像字段抽取正确；有 fromelf/addr2line 时能给出非空符号。

## 10. 建议实现切分（后续编码）

| 模块 | 职责 |
|------|------|
| `ingest` | 识别 armlog 布局、配对 axf |
| `ass_parser` | 正则/状态机抽 ASS 字段 |
| `symbolizer` | axf 多后端反查 |
| `logel_timeline` | 先人工指引，后解析 dat |
| `mem_view` | 基址映射与栈启发式 |
| `report` | Markdown/JSON |
| `rules` | null+offset、线程名、关键字词表 |

技术栈建议：Python 3（解析快、正则强）+ 可选调用外部 `fromelf`；不要一开始绑死 Logel GUI。

---

## 11. 非目标（先不做）

- 自动判定「必现根因」（只给假设与证据链）
- 全自动修复补丁生成
- 非展锐平台 dump 的统一格式（预留接口即可）
- 替代 Logel 的完整协议解码
